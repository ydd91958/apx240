02读懂客户资料

我从客户资料里，读出了四件事

FDE 的第一件事不是写提示词，而是读客户的资料。以下都来自说明书、历史案例与维修工单的交叉阅读。

01

同一个 A310，两种已知根因

H03上游 0.64 · 设备端 0.41 · 有持续漏气声 → 下游接头松动
WO-240-051设备端压力低 · 无漏气声 → 气源滤芯堵塞

所以产品里鉴别规则 DR-01：先确认有没有持续漏气声，再给原因排序

02

最危险的报警码，证据最少

A205红色等级 · 0 个历史案例 · 0 张维修工单
A900黄色等级 · 0 个历史案例 · 0 张维修工单

所以产品里本设备无先例的原因，强度最高只到〔中〕；复机验证须签字确认

03

资料已经 — 天没有更新

WO-240-077最新一张维修工单 · 2026-06-19
此后产线上发生的维修，资料里一条都没有

所以产品里每张处置卡都写明「资料截止 2026-06-19，此后的维修记录未纳入」

04

A900 断连时，面板读数是冻结的

说明书通信中断期间设备状态不可信
风险面板停在 168°C，设备实际可能已经更高

所以产品里读数可信度门控：不拿断连前最后一帧做任何判断

真正缺的不是一个聊天机器人，而是没有被结构化成排查逻辑的现场知识。

04我怎么把它做出来

不是把资料找给模型参考，而是把资料变成它必须遵守的约束

RAG 的思路是把资料找出来给模型参考；这里更进一步：把资料结构化成模型必须遵守的诊断约束，模型只负责理解输入、在约束内排序、说成人话。

诊断约束以结构化规则的形式写在 Agent 的系统提示词中，并非独立的规则引擎。

3条设计原则
  • 规则必须可以机械判定
  • 示例就是规范
  • 不确定，不等于不作为

一次归因 · 安全红线 SAFE-01

  1. 1第一次修复依据行多引了 SAFE-01，加一条禁令复发
  2. 2第二次修复再强调"不要凑条款"复发
  3. 3回到数据定义「异常高温」与「A205 热封温度高」语义重叠，模型其实在严格执行"取更严"找到根因

05它怎么变成客户愿意持续用的产品

现场的问题不是一次性回答，而是一个需要持续维护的业务流程

所以它需要长在一个协同平台里，而不是停在一个 AI 页面上：知识在多维表格，升级走消息，复机走审批，工单回填再更新知识。

05价值测算框架

没有客户数据时，我不虚构 ROI，
只给测算框架

单次非计划停机成本客户提供× 平均停机时长缩短试点测得× 年故障次数客户提供

试点期跟踪四个指标

平均修复时长首次修复率误升级率专家到场次数

→复制路径

  1. 01一台设备 POC验证诊断准确与现场采纳
  2. 02一条产线接入升级推送与工单回填
  3. 03同型号设备复制换表不换约束逻辑
  4. 04生态伙伴配置新设备按模板填写 8 张表

8 张表 = 一套可交付的配置模板，伙伴不需要改约束逻辑，只需要填新设备的资料。

下一步提示词缓存，或拆成路由加子规则

知识同步靠人工

原因同一份知识存在三处：原始表格、多维表格、提示词

下一步让多维表格成为唯一来源

如果明天去见这家工厂，我会先问三个问题

这台设备一次非计划停机，成本是多少？

从报修到工程师到场，现在平均要多久？

手册最后一次更新是什么时候，谁负责？

前两个决定这个方案值不值得买，第三个决定它三个月后还活不活着。

我做的不是一个能回答设备问题的 AI，而是把一套现场排查经验，变成可以执行、可以维护、也可以复制的 Agent。
